# ChatNow — Production Deployment Guide

Two paths:

1. **Free cloud hosting** on Render + Neon + Upstash: a public HTTPS link for portfolio
   demos and interviews, at no cost.
2. **Self-hosted Docker + Nginx TLS** on a Linux VPS: the full multi-instance setup
   (`api-1` + `api-2`) with optional ELK.

---

## 1. Free cloud architecture

```
Browser ──HTTPS / WSS──▶ Render web service "chatnow"  (one origin: https://chatnow-xxxx.onrender.com)
                          ├─ serves the built React app (FRONTEND_DIST)
                          ├─ REST API  /api/*
                          └─ Socket.IO /socket.io
                               │
                ┌──────────────┴──────────────┐
                ▼                             ▼
        Neon PostgreSQL                Upstash Redis
   (data + uploaded files)     (rate limits, presence, revocations)
```

**Why one service instead of a separate frontend host.** With the site on one domain
and the API on another, the refresh cookie becomes a *third-party* cookie, which Safari,
Firefox and Brave block, and Chrome is phasing out, so users would be signed out on
every reload. Serving everything from one origin keeps the cookie first-party with
`SameSite=Strict` and needs no cross-origin rules.

### Free-tier limits (checked 2026-11-19; providers change these, so re-check before relying on them)

| Service | Free tier | Effect on ChatNow |
|---|---|---|
| **Render** web service | Sleeps after **15 min** without traffic and takes about **1 min** to wake; filesystem wiped on every restart, redeploy and sleep; 750 instance-hours per month | The first visit after a quiet period loads slowly. Uploaded files are therefore stored in PostgreSQL (`STORAGE_DRIVER=database`). |
| **Neon** PostgreSQL | 1 GB storage per project, 100 CU-hours per month, scales to zero after 5 min idle | Plenty for messages; uploads share the 1 GB (10 MB max per file). |
| **Upstash** Redis | **500K commands per month**, 256 MB | Presence costs 1 command per open tab per minute (~43K per tab left open all month). Cross-instance Pub/Sub is off on Render (one instance) to save commands. |
| **ELK** | No free hosted option (Elasticsearch needs 1–2 GB RAM; Elastic Cloud is a 14-day trial) | Demonstrated locally with Docker; on Render use the dashboard's log viewer. |

Sources: [Render FAQ](https://render.com/docs/faq), [Neon plans](https://neon.com/docs/introduction/plans), [Upstash pricing](https://upstash.com/docs/redis/overall/pricing).

**Paid upgrades** remove the sleep (Render from $7/month), allow more than one
instance, and add persistent disks. For real traffic, move uploads to S3-compatible
object storage.

## 2. Step-by-step free deployment

You need: a GitHub account with this repository pushed to it, and free accounts on
Render, Neon and Upstash. Pick the **same region** for all three (the blueprint uses
Render's **Oregon** region, so choose **US West (Oregon) / us-west-2** on Neon and Upstash).

### Step 1 — PostgreSQL on Neon

1. Create a project (PostgreSQL 17, region US West Oregon).
2. On the project dashboard, open **Connect**, turn **off** "Connection pooling", and
   copy the connection string. It looks like
   `postgresql://<user>:<password>@<host>.neon.tech/neondb?sslmode=require`.
   Use the direct (non-pooled) string: Prisma migrations need a direct connection.
3. Nothing else to set up: the first deploy runs the migrations, which enable the
   `citext` and `pg_trgm` extensions (both available on Neon).

### Step 2 — Redis on Upstash

1. Create a Redis database (region us-west-2, free plan, TLS on).
2. Copy the **TLS** URL: `rediss://default:<password>@<host>.upstash.io:6379`
   (note `rediss` with two s's).

### Step 3 — The app on Render

1. Render dashboard → **New → Blueprint** → connect GitHub → choose this repository.
   Render reads [render.yaml](../render.yaml).
2. When asked for the values marked `sync: false`, paste:
   - `DATABASE_URL`: the Neon string from step 1
   - `REDIS_URL`: the Upstash string from step 2
3. Apply. Render installs and builds both apps, runs `prisma migrate deploy`, starts the
   server, and polls `GET /api/health`. The first build takes several minutes.
   `JWT_ACCESS_SECRET` is generated by Render; the allowed origin is taken from
   Render's `RENDER_EXTERNAL_URL` automatically.
4. Check it (replace the URL with yours):

   ```powershell
   Invoke-RestMethod https://chatnow-xxxx.onrender.com/api/health
   ```

   Expect `status: ok`, `database: up`, `redis: up`.

**Never** put real values for `DATABASE_URL`, `REDIS_URL` or `JWT_ACCESS_SECRET` in the
repository; they live only in Render's environment settings.

## 3. Self-hosted multi-instance Docker + HTTPS/WSS (Linux VPS)

For the full setup (`api-1` + `api-2` behind Nginx, PostgreSQL, Redis, optional ELK)
on one VPS (2 GB RAM without ELK, 4 GB+ with it):

1. Clone the repo and create `.env` and `backend/.env` from the `.env.example` files.
2. Obtain TLS certificates (for example Let's Encrypt with Certbot).
3. Use `infrastructure/nginx/nginx.tls.conf` for the `nginx` service, mount the
   certificates read-only, and publish ports 80 and 443.
4. Set `COOKIE_SECURE=true` and `CORS_ORIGINS=https://<your-domain>`
   (`COOKIE_SAME_SITE` stays at its default, `strict`).
5. Launch:

   ```bash
   docker compose --profile full up -d --build
   docker compose --profile full --profile elk up -d --build   # with ELK
   ```

Docker uses `STORAGE_DRIVER=disk` with a shared volume, so both API instances see
every uploaded file.

## 4. Production smoke test

Before sharing the link:

- [ ] `GET /api/health` returns `200` with `database: "up"` and `redis: "up"`.
- [ ] The site loads over `https://`; DevTools → Network → WS shows a `wss://` connection.
- [ ] Register two users in two browsers (or a normal and a private window).
- [ ] Reload both: both stay signed in; Local Storage contains no tokens.
- [ ] Direct messages arrive instantly; ticks go sent → delivered → read; they survive a reload.
- [ ] Group chat, typing indicator, reply, edit, delete, reactions and search work.
- [ ] Upload an image; it still loads after the service has slept and woken up.
- [ ] A third user gets `404` for a conversation they are not in.
